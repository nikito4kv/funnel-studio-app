# Этап 3: движок

Пакет `runtime/` – собственный движок воронок. Он исполняет **граф Студии напрямую** (без выгрузки в
yaml), держит таймеры в Postgres и обслуживает много запусков одним процессом. Воронка, опубликованная
командой, начинает работать без сборки образа и без рестарта; люди, которые уже внутри, не теряются.

## Как запустить (по шагам)

```bash
# 1. Postgres в Docker (один раз; снести – docker rm -f fs-runtime-pg)
docker run -d --name fs-runtime-pg -e POSTGRES_USER=fs -e POSTGRES_PASSWORD=fsruntime \
  -e POSTGRES_DB=fs_runtime -p 127.0.0.1:55432:5432 postgres:16
#    остановить / поднять снова: docker stop fs-runtime-pg / docker start fs-runtime-pg

# 2. Воронку – в хранилище Студии (или нарисовать в редакторе)
uv run python -m runtime import-repo webinar/funnel.yaml     # → data/funnels/webinar__funnel.json

# 3. Завести запуск и привязать бота. В базу пишется ССЫЛКА env:ИМЯ, сам токен – нет.
#    Токен берётся из окружения или из файла STUDIO_ENV_FILE (по умолчанию
#    ~/.funnel-studio/test_bot.env, строка STUDIO_TEST_TG_TOKEN=…).
uv run python -m runtime tenant add studio-test --title "Тест Студии" \
  --bot-env STUDIO_TEST_TG_TOKEN --from-launch webinar     # канал / эфир / подарок / static из launch.yaml

# 4. Опубликовать (можно и при запущенном движке – граф подменится на лету).
#    Удобнее – кнопкой «Опубликовать» в Студии (см. «Публикация из Студии в движок»). CLI берёт
#    ОПУБЛИКОВАННУЮ версию Студии (webinar__funnel@3 – конкретную); нет её – черновик с
#    предупреждением; --draft – черновик явно.
uv run python -m runtime.publish studio-test webinar__funnel --comment "первая версия"

# 5. Запустить / посмотреть / остановить
uv run python -m runtime run            # все запуски, все боты; health: http://127.0.0.1:8781/health
uv run python -m runtime status         # очередь, позиции, версии (или GET /status)
uv run python -m runtime stop           # корректная остановка (или Ctrl+C в окне движка)
```

Прочее: `tenant list`, `tenant set <slug> channel.chat_id=-100… dnd.enabled=true` (применяется без
рестарта), `hurry <slug> [--uid N]` – **только для ручной проверки**: ставит ожидающие шаги на
«сейчас» по порядку, чтобы не ждать часами. Переменные: `STUDIO_RUNTIME_DSN` (база),
`STUDIO_DATA` (папка данных Студии), `BOT_REPO_PATH`, `STUDIO_TG_PROXY` (`socks5://…`, как
`TELEGRAM_PROXY` в bot-engine), `STUDIO_RUNTIME_PORT` (8781).

⚠️ Один токен – один поллер. Пока `runtime run` поллит тестового бота, второй процесс с тем же
токеном (и bot-engine, и второй `runtime run`) получит `TelegramConflictError`.
Если тестового бота уже поллит движок на сервере (см. `deploy/compose.yaml`), локально для ручных проверок нужен свой, другой тестовый бот.

## MAX: как подключить бота

```bash
# токен MAX-бота – в окружение или в STUDIO_ENV_FILE (в базу пишется только env:ИМЯ)
uv run python -m runtime tenant add webinar --max-bot-env WEBINAR_MAX_TOKEN
# тот же бот у второго запуска = общий («зонтичный») бот, у каждого запуска своя метка входа
uv run python -m runtime tenant add extra --max-bot-env WEBINAR_MAX_TOKEN   # метка «extra_»
#   --max-prefix <метка>   метка входа (по умолчанию «<slug>_»)
#   --max-default          этот запуск – для входа без метки (по умолчанию – первый привязанный)
uv run python -m runtime tenant set webinar channel.max_link=https://max.ru/join/… \
    channel.max_chat_id=-100… webinar.stream_url_max=https://…     # ссылки и канал MAX
```

Ссылки людям: `https://max.ru/<бот>?start=webinar_reg_vk_post_…` – метка `webinar_` выбирает
запуск и снимается, остаток разбирается как в Telegram (`reg_…`, `ref_…`, UTM). `status` и
`tenant list` показывают MAX-ботов, метки и какой бот общий. Бот, привязанный при работающем движке,
начнёт поллиться после рестарта. ⚠️ Тот же токен не должен поллить никто другой (если общий MAX-бот уже поллит
другой процесс, переносить его можно только целиком). Прокси для MAX
не нужен; другой адрес API (тест, стенд) – `STUDIO_MAX_API_BASE`.

**Роутинг апдейтов общего бота** (`runtime/platforms/max_hub.py`):
- вход – `bot_started` (первый раз) или сообщение `/start <метка>` (повторный вход в MAX приходит
  так): самая длинная подходящая метка → её запуск; метки нет / чужая → запуск по умолчанию (его нет –
  вход не принят, в логе предупреждение);
- кнопка: payload `f:<slug>:…` (каждая callback-кнопка несёт слаг, bot-engine §36); слаг чужого для
  бота запуска или кнопка без слага в воронки не попадают, только отметка на кнопке;
- обычное сообщение и контакт – в запуск, где от человека ждут ответа (телефон/почта), иначе где
  его позиция свежее;
- `bot_stopped` / `dialog_removed` и ошибка 403 при отправке – человек заблокировал бота: блок
  во всех запусках этого бота, задачи отменяются; новый вход снимает блок.

Человек MAX – отдельный участник запуска (`participants`/`positions`/`jobs` ключуются платформой),
с его Telegram-записью не сливается; очередь, анти-дубль 90 с, позиции и повторный /start работают
так же. Маркер long-poll хранится в `bots.poll_marker` и двигается после разбора пачки.

## Схема (`runtime/migrations/001_init.sql`, `002_max_bots.sql`, таблица `schema_version`)

| Таблица | Что |
|---|---|
| `tenants` | запуск: slug, название, `settings` JSONB – канал, эфир, ВИП, подарок, ночной режим, откуда брать static, политика повторного /start, `max_parallel_fires` |
| `bots` | боты запуска (`platform` tg/max); токена нет – `secret_ref = env:ИМЯ`, id и username из getMe / `/me`; у MAX – `poll_marker` |
| `bot_tenants` | какие запуски обслуживает MAX-бот (общий бот – несколько строк): метка входа, запуск по умолчанию |
| `funnel_versions` | неизменяемые версии: граф JSONB, кто/когда/комментарий, режим, отчёт по живым людям |
| `participants` | человек запуска: имя, телефон, почта, UTM **первого** входа, trigger, заблокировал ли |
| `positions` | явная позиция: воронка, версия, последний шаг (по id), ветка, эфир человека, статус, чего ждём (контакт/почта) |
| `jobs` | очередь: шаг, вид `fire/also/skip`, `run_at`, статус, попытки, аренда, причина, ключ идемпотентности; «один ожидающий таймер на шаг человека» – частичный уникальный индекс |
| `sent_messages` | что ушло (id сообщений, у MAX – строковые `ext_message_ids`, ок/ошибка); одна строка на задачу – по ней повтор задачи не шлёт второй раз |
| `actions` | лог событий: каждый /start с сырым payload, шаги, клеймы, контакты, «гейт не проверен», «не поддерживается» |
| `media_cache` | (sha256 файла, бот, вид) → file_id Telegram; у MAX вид `max_image`/`max_video` → токен вложения |

Виды шагов (`004_steps.sql`):

| Таблица | Что |
|---|---|
| `survey_responses` | ответы опроса человека: `answers` (ключ – `survey.qid`), `submitted_at` – опрос пройден (источник для гейта `survey_done`: `runtime.steps.survey.is_done`) |
| `survey_prompts` | заданный вопрос: открыт / отвечен, отмеченные варианты multi, id сообщения с кнопками |
| `survey_edits` | `survey.edit`: какой шаг встанет на место сообщения вопроса |
| `air_pins` | закреп эфира человека: сообщение, нарисованное состояние, текст шага под шапкой, `next_at` – когда перерисовать, `pin_at` – отложенное закрепление |

`007_max_steps.sql` – виды шагов в MAX: id сообщения MAX – строка («mid.…»), поэтому у
`survey_prompts` и `survey_edits` есть `ext_message_id text` (у Telegram пусто), а
`survey_edits.message_id` может быть пустым. Миграции движок применяет сам при старте
(`runtime.db.migrate`, таблица `schema_version`); руками ничего накатывать не нужно.

## Как устроено

```
runtime/
  engine_lib/     перенесено из bot-engine библиотекой (шапка «откуда, коммит, что поправлено»):
                  branch.py, dnd.py, render.py, video_meta.py, deep_link.py, phone.py
  graph.py        граф Студии в памяти: шаг по id, стрелки по видам
  planner.py      когда уйдёт шаг: часы/эфир, skip_if_past и 120 с, min_delay_seconds, DND, also_fire
  executor.py     шаг: анти-дубль 90 с → jump/телефон/почта → гейты → отправка → on_done → also_fire
  sender.py       отправка в Telegram: подпись >1000 отдельно, кружок → видео → текст, файлы байтами
  gateway.py      события людей: /start, контакт, кнопка-клейм, текст (почта, телефон), блокировка
  worker.py       очередь: SKIP LOCKED, аренда, семафоры, повтор с паузой
  registry.py     запуски и версии в памяти, горячая подмена
  gates/          источники данных для гейтов: касса (вебхук), Bizon, клики (/go, /govip)
  publish.py      публикация, отчёт по живым, режимы new-only / migrate
  steps/          виды шагов сверх фундамента (исполнитель зовёт fire() после гейтов и
                  after_send() после обычной отправки):
                  survey.py – опрос, call.py / sms.py + providers.py – звонок и SMS,
                  air_pin.py – закреп отсчёта до эфира, rich.py – статья,
                  chain.py – переход в другую воронку, config.py – их настройки запуска
  service.py, runner.py, cli.py, status.py
  platforms/      MAX: max_api.py (клиент), max_hub.py (боты, long-poll, роутинг апдейтов по
                  запускам), max_steps.py (контент шага, телефон, канал в MAX), max_sender.py
                  (отправка), max_html.py (HTML → MAX); в executor/gateway – только точки вызова
```

- **Итог шага – одной транзакцией.** Шаг не «планирует следующий в конце работы» (из-за этого в
  bot-engine авария между отправкой и планированием убивала весь остаток цепочки). Следующие задачи,
  сдвиг позиции, события и пометка «задача выполнена» коммитятся вместе. Упал процесс до коммита –
  аренда истечёт, задачу возьмут снова, а запись в `sent_messages` не даст отправить второй раз.
  Запись «отправляю» делается ДО вызова Telegram: при сомнении движок скорее не повторит
  сообщение, чем задвоит его.
- **Главное правило (инцидент 15.05):** ошибка отправки, гейта или любая другая внутри шага → лог +
  `on_done` всё равно. Исключение – человек заблокировал бота: он помечается, его задачи отменяются.
- **Пачки таймеров :** шагов одного запуска одновременно не больше
  `max_parallel_fires` (8), всего в работе – не больше соединений пула минус запас. Проверено тестом:
  600 шагов в одну секунду, упор ровно в 8, пул не исчерпан, ни одной ошибки.
- **Время:** внутри всё tz-aware UTC и только от часов движка (`runtime/clock.py`), в логах и
  `status` – МСК. Тесты перематывают время управляемыми часами.
- **Порядок блокировок** один везде: человек → позиция → задачи (события и финал шага не ждут друг
  друга по кругу).

## Публикация и люди внутри – контракт `PublishedSource`

Источник графа – любой объект с протоколом `runtime.publish.PublishedSource`
(`load(name) -> Funnel`, `describe(name) -> str`). Основной – `StudioVersionSource`: хранилище версий
Студии `data/studio.db`, имя `<запуск>__<воронка>` – опубликованная версия, `…@N` – версия N,
`describe` → `studio:<имя>@vN`; им пользуются и кнопка Студии, и CLI. Черновик – `StudioStorageSource`,
файлы `data/funnels/<запуск>__<воронка>.json` (CLI `--draft`). Кнопка «Опубликовать» Студии вызывает
тот же `runtime.publish.publish(pool, tenant_slug, funnel, comment=…, author=…, mode=…,
redirects={старый: новый}, dry_run=…)` – он возвращает `PublishReport` (`.text()` по-русски,
`.to_json()` для интерфейса) или бросает `PublishError` с отчётом.

Что делает публикация:
1. проверяет граф моделью Студии;
2. считает отчёт: сколько задач ожидает на каждом шаге («у N чел. запланирован этот шаг»), кто ждёт
   ответа, какие шаги исчезли (по id), у каких изменилось время;
3. **migrate** («перевести всех»): исчез шаг, на котором есть люди, а карты нет → отказ с текстом
   «шаг «X» удалён, а у N чел. он запланирован – укажите `--map X=<новый>` или оставьте надгробием».
   Надгробие (шаг, ставший `jump` с тем же id – так удаляет редактор) карты не требует. С картой
   задачи переносятся на новый шаг; у шагов с часами/от эфира время пересчитывается
   (`resolve_step_target` + `skip_if_past`), у остальных сохраняется оставшаяся задержка;
4. **new-only** («только новым», по умолчанию): уже идущие доезжают по своей версии (граф старой версии
   держится в памяти, пока на ней есть задачи или люди), новые /start – по новой;
5. пишет версию и шлёт `NOTIFY fs_versions` – запущенный движок подменяет граф без рестарта.

Откат – публикация прошлой версии тем же путём (новым номером). `--dry-run` – только отчёт.

## Источники данных для гейтов (`runtime/gates/`, миграция `006_gates.sql`)

Условие шага сводится к факту о человеке («оплатил ВИП», «был на эфире дня N», «кликнул ссылку с
меткой X») с тремя состояниями: да / нет / **не знаем**. «Не знаем» – источник не настроен, упал или
данных ещё нет. Политика при «не знаем»:

| Гейт | Направление | Нет данных |
|---|---|---|
| `paid`, `course_paid`, `attendance: was`, «кликнул» (`link_click`), `has_lm` | только тем, у кого факт есть | **fail-safe** – шаг пропускается, `gate_failsafe` в `actions` |
| `not_paid`, `not_course_paid`, `attendance: was_not`, `no_link_click`, `survey_done`, `no_manager_dm`, `registered_windows` | дожим тем, у кого факта нет | **fail-open** – шаг уходит, `gate_unchecked` в `actions` (§24: лишний дожим дешевле молчания) |

`survey_done` («не прошёл опрос») читает ответы опроса движка (`survey_responses.submitted_at`,
`runtime.steps.survey.is_done`) – он всегда «по данным», fail-open только при сбое базы.
«Кликнул» (`conditions.link_click`) – **поле Студии**: у движка bot-engine такого гейта нет
(`FunnelStep` – `extra="forbid"`), поэтому в yaml оно не выгружается
(`studio.convert.mapping.STUDIO_ONLY_PATHS`); экспорт и проверка (правило 83) предупреждают,
что в старом боте шаг уйдёт всем. В редакторе – «＋ Добавить условие → кликнул ссылку»,
на карточке значок 👆; симулятор его учитывает (персона «Кликнул ссылку»).

«Зарегистрировался не в эти часы» (`conditions.registered_windows`, в yaml – `skip_if_registered_msk`,
bot-engine): окна МСК «ЧЧ:ММ-ЧЧ:ММ», начало входит, конец нет. Время регистрации – последняя
удачная отправка входного шага воронки (входы веток, когорт или первый шаг) из `sent_messages`, так
что повторный /start считается заново. Не нашли – шаг уходит. Рядом два поля того же коммита:
`schedule.min_delay_seconds` («не раньше чем через N после того, как шаг запланирован» – у шага со
временем; для прошедшего часа при «всё равно отправить» – вместо 120 с) и
`Funnel.resend_entry_on_repeat` (повторный /start в окне анти-дубля шлёт первое сообщение ещё раз
задачей мимо анти-дубля, таймеры не трогает; `/start` возвращает `resent`).

Пропуск по данным пишется как обычный `gated_out`. Публикация (`runtime.publish`) сверяет условия
шагов с настройками запуска и пишет в отчёт: «шаги «X» требуют данных, а их нет: не настроен источник
оплат ВИПа … Они НЕ уйдут никому» / «дожимы «Y» … уйдут ВСЕМ». Публикацию это не блокирует – движок
и без источника ведёт себя безопасно.

Настройки – в `tenants.settings`, секреты – только ссылками `env:ИМЯ`:

```bash
uv run python -m runtime tenant set <slug> payments.enabled=true payments.secret=env:PAYMENTS_WEBHOOK_SECRET \
  'payments.vip_tariffs=["<uuid тарифа>"]' payments.paid_from=2026-09-01 'payments.on_paid={"vip":"s_vip_thanks"}'
uv run python -m runtime tenant set <slug> bizon.enabled=true bizon.token=env:BIZON_API_TOKEN bizon.room=<зал>
uv run python -m runtime tenant set <slug> links.enabled=true links.base_url=https://<публичный адрес движка>
```

**Оплаты** (`payments.py`). Касса шлёт вебхук на `POST /payments/callback` (или
`/t/<запуск>/payments/callback`): JSON как у приёмника bot-engine (`common/payments/router.py`), подпись
`X-Payment-Signature` = HMAC-SHA256 тела общим секретом. Подпись проверяется секретами запусков;
платёж видят только запуски, чьим секретом она сошлась (`gate_payments.verified_refs`). Повтор того же
статуса – `duplicate`, ничего не делает; смена статуса (`refunded`) – гейт сразу видит возврат.
Привязка к человеку: по id из ссылки (`meta.id` / `client_id` – его кладёт прокси `/govip`, запасные –
`customer.telegram_id`, `utm.content` цифрами), по телефону – **только** при `match_by_phone: true`
(§34: тот же тариф может продавать другой бот), оплаты раньше `paid_from` не считаются. Гейт читает
таблицу оплат при каждой проверке. В момент привязки – событие `paid` в `actions` и, если задан
`payments.on_paid.vip|course`, запуск этого шага человеку (отбивка «оплата прошла»; шаг ищется по
ключу в воронке, где у человека позиция).

**Эфир** (`bizon.py`). Отчёты Bizon365 (`webinars/reports/getlist` + `getviewers`, `X-Token`)
кэшируются в `gate_bizon_*`: список – не чаще `list_ttl_seconds`, зрители закрытой сессии – один раз.
Зал: `bizon_room_max` шага (MAX) → `bizon_room` шага → зал воронки → `bizon.room(_max)` запуска.
Окно – **на дне самого шага** (§32а: эфир человека + `day_offset`/`day_offset_by_branch`, повтор ветки
для `anchor: repeat`), длина `gate_window_hours`, с запасом `window_lead_minutes` до начала. Зритель
ищется по `id=` в адресе (его дописывает `/go` при переходе на Bizon, `bizon.autologin`) или по
телефону. §27: пока эфир идёт, отчёта нет (getviewers → 403) – это «не знаем», а не «не был»; гейты
«был / не был» ставить после эфира. Переход по ссылке эфира через `/go` (адрес содержит имя зала,
в окне) тоже считается «был» (`bizon.count_link_clicks`).

**Клики** (`links.py`). При включённых `links` кнопки-ссылки и ссылки в тексте отправляются как
`{base_url}/go/<code>?u=<id>&p=<платформа>` (302 + запись в `gate_clicks`); t.me / max.ru / vk,
`tg://` и web_app не оборачиваются. Метки как в bot-engine: кнопка `funnel_<шаг>`, текст `text_<шаг>`,
ВИП `vip_<шаг>` – гейты импортированных воронок (`no_link_click: "funnel_s_d3_"`) работают без правок.
`{vip_link}` → `{base_url}/t/<запуск>/govip?u=&pl=&s=<шаг>` → ВИП-страница с `id`, `tg_id`
(`max_id` у MAX), именем, телефоном, исходными UTM и `utm_content=vip_<шаг>` (касса вернёт `id` в
вебхуке). §22: клик берётся из событий, не из UTM. §26: в MAX кнопки-ссылки оборачиваются так же
(`/go/…&p=max`, `links.wrap_max_rows`), а ссылки из текста – нет: человеческий клик в MAX – только
кнопка и ВИП-прокси. Переходы превью-роботов (TelegramBot и т.п.) пишутся с `is_bot` и не считаются.

| Таблица | Что |
|---|---|
| `gate_payments` | платёж кассы: внешний id (уникален), статус, тариф, id/телефон плательщика, какими секретами подписан, сырое тело |
| `gate_payment_links` | привязка платежа к человеку запуска (журнал события `paid`) |
| `gate_bizon_sync`, `gate_bizon_reports`, `gate_bizon_viewers` | кэш Bizon по аккаунту: когда читали список, сессии залов, зрители |
| `gate_links`, `gate_clicks` | прокси-ссылки (код → адрес, метка) и клики (кто, откуда: кнопка/текст/ВИП, робот ли) |

## Публикация из Студии в движок (кнопка «Запустить в боте»)

**Как это видит человек** (переделано после живого теста – было непонятно, куда и в
какой бот ушла воронка, почему правки после публикации не пришли в бот и почему пустые шаги «прошли»):

| было | стало |
|---|---|

- **Три кнопки – три разных действия.** «Сохранить черновик» – правки остаются в Студии, бот их не
  видит (об этом говорит и подсказка кнопки, и сообщение после сохранения). «Запустить в боте…» –
  версия фиксируется и уходит в бота. «Проверить в боте ↗» – открыть бота и пройти воронку самому.
- **Шапка говорит, что в боте:** «● Работает в боте @funnel_studio_TEST_bot · версия 2» / «Ещё не
  запущена ни в одном боте» / «Нет связи с ботами». Если в редакторе есть изменения против того, что
  работает в боте (в том числе несохранённые – дифф считается по графу редактора), под бейджем –
  «Есть правки, которых нет в боте – нажмите «Запустить в боте»». Сравнение – по журналу
  `engine_publishes` и `source = studio:<воронка>@vN` последней версии в движке; версия, отправленная
  не из Студии (командной строкой), – всегда «есть правки». Раскладка, полосы и заметки правками не
  считаются. Без базы движка шапка как на этапе 2A («Черновик · изменено N» / «Опубликована vN»).
- **Диалог сверху вниз:** «Бот: @funnel_studio_TEST_bot (Тест Студии)» (username из таблицы `bots`
  движка; «не отправлять в бота» – только сохранить версию) → одна-две фразы последствий из пробной
  публикации: «Новые люди получат эту версию. 1 человек уже внутри – он дойдёт по старой. Боевые боты
  не затрагиваются» (последняя фраза – только если все боты запуска тестовые: не найдены в `username:`
  файлов `launches/*/launch.yaml` bot-engine и помечены как тестовые – `test` в имени или токен
  `env:STUDIO_TEST_*`) → «Сделать стартовой» → проблемы, которые нужно исправить (красным) → «Стоит
  проверить» (жёлтым) → «Что изменилось с версии N». Режим для тех, кто внутри («Доходят по старой» /
  «Перевести всех на новую»), отчёт по шагам, куда перевести людей с удалённых шагов, предупреждения
  движка и проверка выгрузки для bot-engine – под «Подробнее», свёрнуто (разворачивается само при отказе
  и в режиме «перевести всех»). Главная кнопка – по действию: «Запустить в боте @…» или «Сохранить
  версию». Служебных слов (движок, запуск-tenant, дифф, блокер, надгробие, команды терминала,
  переменные окружения) в диалоге нет – e2e это проверяет.
- **Стартовая воронка.** /start бота ведёт в `entry_funnel` запуска (или первую по имени). Если
  воронка не стартовая – галочка «Сделать стартовой: /start в боте будет вести сюда» (у тестового бота
  включена по умолчанию, у боевого – нет). Ставит `settings.entry_funnel` и шлёт `NOTIFY fs_tenants` –
  движок перечитывает настройки без рестарта (`engine.make_entry` в запросе, `EngineLink.set_entry`).
- **«Проверить в боте»** – `https://t.me/<бот>?start=studio_test_<id воронки>` (`runtime/studio_test.py`;
  id, который не влезает в 64 символа `A-Za-z0-9_-`, – `studio_th_<хэш>`). Такой /start запускает
  человека в ЭТУ воронку с начала, даже если она не стартовая: его ожидающие задачи в ней отменяются,
  анти-дубль 90 с для нового прохода не действует (отметка `start_fresh` в `actions`), UTM из служебного
  payload не берутся. Безопасно: человек перезапускает только себя. Воронки нет в запуске – обычный /start.
- **Пустые шаги** (`studio/model/emptiness.py`, в браузере – правило 84 панели «Проверка»): шаг, которому
  нечего отправить (ни видимого текста, ни картинки, ролика, кружка, статьи), блокирует запуск –
  «Шаг «Текст» пустой – бот ничего не отправит»; «сообщение с картинкой» без картинки, видео без ролика,
  пустой только в Telegram – предупреждения. Публикация движка (`runtime.publish`) пишет их в отчёт.
  Если пустой шаг всё же дошёл до движка (опубликован раньше, CLI) – в `actions` `empty_step` и WARNING
  в логе, цепочка идёт дальше.

Одна кнопка: версия записывается в хранилище Студии (как на этапе 2A) и сразу уходит в движок –
через тот же `runtime.publish.publish(...)`, что и CLI. Граф для движка берётся **из хранилища версий
Студии** (`StudioVersionSource`, ровно та версия, что только что записана), а не из черновика.

**Как включить.** Серверу Студии нужен адрес базы движка:

```bash
STUDIO_RUNTIME_DSN=postgresql://fs:fsruntime@127.0.0.1:55432/fs_runtime uv run python -m studio.server
# или: uv run python -m studio.server --runtime-dsn postgresql://…
```

Нет адреса – кнопка в шапке называется «Опубликовать…», в диалоге – «Студия пока не подключена к
ботам – версия сохранится только здесь», главная кнопка «Сохранить версию» (как на этапе 2A). База не
отвечает – «Нет связи с ботами», сохранить можно только в Студию.

**Что под капотом диалога:**
- **Бот** – выбор из `tenants` движка (в списке – username бота и название запуска); выбор
  запоминается для воронки (`data/studio.db`, таблица `engine_targets`). Под «Подробнее» – что сейчас
  работает в боте (версия, когда, кто; «запущена не из Студии», если из CLI).
- **Режим** (под «Подробнее»): «Доходят по старой» (`new-only`, по умолчанию) / «Перевести всех на
  новую» (`migrate`).
- **Отчёт по живым людям** – пробная публикация (`dry_run`) при каждом изменении бота, режима или
  карты: фразы последствий сверху, а под «Подробнее» – «В боте @… работает прошлая версия этой воронки
  – её сменит новая. Внутри воронки 5 человек», по шагам – «у 3 человек запланирован этот шаг»,
  «2 человека ждут, когда пришлют контакт» (почту), и что будет с шагом: не меняется / новый вариант /
  изменилось время / исчез.
- **Куда перевести людей с удалённых шагов** (только «Перевести всех», только исчезнувшие шаги, на
  которых есть люди) – подставляется само: шаг с тем же именем → куда вёл переход (удалённый шаг) в
  версиях Студии → следующий по стрелкам шаг, который есть в новой версии. Поправить – выпадающим
  списком («не выбрано» – убрать).
- **Отказ движка** (`PublishError`) – красным сверху: «Бот не примет эту версию: …» (подсказки CLI
  `--map` и слово «надгробие» заменяются человеческими – `studio.versions.engine.human`); кнопка
  недоступна. Проблемы проверки Студии по-прежнему блокируют.
- **Автор** – поле рядом с комментарием (пока без входа; имя запоминается в браузере).
- Черновик совпадает с последней версией, а в выбранный бот она ещё не уходила – главная кнопка
  «Запустить в боте @…» отправляет её (`POST …/versions/{N}/engine`); уже там – «Изменений нет – в боте
  … уже работает версия N».

**Честное состояние.** Перед записью – пробный прогон в движке: отказал – не пишется ничего, ни в
Студию, ни в движок (409). Прошёл – версия Студии записывается, затем настоящая публикация в движок.
Если движок отказал уже на ней (за секунду поменялись люди, база упала), версия остаётся
«опубликованной» в Студии, но в журнале отправок (`engine_publishes`) – «не ушла» с причиной;
в «Истории» у версии кнопка «Запустить в боте @…». Таблица `versions` не меняется
(она неизменяема), поэтому «ушла ли версия в движок» – только по журналу.

**История версий** показывает у каждой версии, куда она ушла: «→ запущена в боте
@funnel_studio_TEST_bot · только новым» или «✕ в бот @… не ушла: …» (номер версии в базе движка – в
подсказке). В движке у версии `source = studio:<воронка>@vN`, `published_by` – автор, `comment` –
комментарий Студии.

**Откат** – как в 2A: «Откатить сюда» (черновик = копия vN) → «Опубликовать» – в движок уходит тем
же путём новой версией. Отправить в движок можно только опубликованную версию Студии
(`POST /api/funnels/{имя}/versions/{N}/engine`), иначе Студия и движок разошлись бы молча.

| Адрес | Что |
|---|---|
| `GET /api/engine` | подключён ли движок, адрес (без пароля), запуски: боты (username, тестовый ли), стартовая воронка, политика /start |
| `GET` / `PUT /api/funnels/{имя}/engine` | запуск воронки (запоминается), что сейчас в движке, журнал отправок; `in_bot` (версия в боте, номер Студии), `is_entry`, `test_link` («Проверить в боте») |
| `POST /api/funnels/{имя}/engine/check` | пробная публикация: отчёт, кто ждёт контакт/почту, отказ, подсказка карты |
| `POST /api/funnels/{имя}/publish` + `engine: {tenant, mode, redirects, make_entry}` | версия Студии + движок одной операцией; `make_entry` – сделать стартовой |
| `POST /api/funnels/{имя}/versions/{N}/engine` | отправить опубликованную vN (повтор после отказа, другой запуск) |

## Что поддерживается в фундаменте

- `/start`: разбор payload как в bot-engine (`reg_`/`ref_`/utm/…), UTM – первый вход, каждый /start – в
  `actions`; ветка `branch_router` и эфир человека; `entry_variants` и формулировки когорт (`variants`);
  повторный /start – политика запуска: `engine` (как движок, §23: недавний вход и живые таймеры –
  ничего не трогаем, иначе с начала), `keep`, `restart`. **Почему повторный /start «молчит»:** при
  `engine` и `keep` он намеренно ничего не трогает, пока воронка идёт (в `actions` – `start_ignored` с
  причиной: «вход был меньше 90 с назад и следующие шаги уже запланированы»); если воронку всё же
  перезапустили, а первый шаг уходил меньше 90 с назад – анти-дубль его не шлёт (`dup_skip` с
  причиной). Для проверок: политика `restart` (тестовый бот) – каждый /start с начала без анти-дубля
  (отметка `start_fresh`), а у любого бота – кнопка Студии «Проверить в боте» (`studio_test_<воронка>`);
- шаги `text`, `photo` (и альбом), `video`, `animation`, `video_note` (+ `video_fallback`),
  `phone_request` (кнопка контакта, «дал / не дал за N с / уже известен», номер текстом),
  `email_request` (проверка формата, повтор, «не прислал»), `jump`-надгробие; закреп `pin`;
- кнопки-ссылки (кнопка без рабочей ссылки не показывается – иначе Telegram отклонил бы всё
  сообщение), web_app, кнопка-клейм (отменяет ожидающий `on_done`, кроме `keeps_chain`; без цели –
  всплывающий `ack_text`);
- время: `absolute_time_msk` + `day_offset` / `webinar_offset_minutes` + `anchor` / `*_by_branch`,
  `skip_if_past` и 120 с, `after_start_seconds`, ночной режим и `dnd_exempt`, `also_fire` без DND;
- гейт «в канале / не в канале» – через getChatMember;
- гейты оплаты, эфира и кликов – по источникам данных (см. «Источники данных для гейтов»);
- медиа: `./static/…` из `data/media` Студии или `static` запуска bot-engine, байтами, file_id в кэше
  по (sha256, бот); у видео ширина/высота/длительность;
- плейсхолдеры `render.py` (`{Имя}`, `{channel.link}`, `{webinar.*}`, `{vip_link}`, `{utm_*}`, …);
- **MAX** (семантика движка bot-engine): общий бот на несколько запусков (см. «MAX: как подключить
  бота»); `content.max` – `None` «как в TG», пустое – «в MAX этого нет», `text_max` у когорты;
  `max_video_note_caption: false`; `{channel.link}` → `channel.max_link`, `{stream_url}` →
  `webinar.stream_url_max`; HTML → MAX (`<tg-time>`, `<blockquote>` снимаются); кружок = видео с
  подписью; медиа и длинный текст – одним сообщением; альбом; файлы байтами, токен вложения в кэше;
  claim-кнопка `f:<slug>:c:<шаг>`, callback-кнопки – только из `content.max.buttons`; запрос
  телефона: без `manual_phone_max` пропускается (`on_skip_if_phone_known` → `on_skip` →
  `on_contact`), с ним – кнопка «поделиться контактом» и ожидание (номер текстом тоже годится);
  почта – как в TG; гейт канала – участники канала MAX (`channel.max_chat_id`).

## Виды шагов (`runtime/steps`)

Семантика – как у движка bot-engine; где сознательно иначе, сказано «отличие».

- **Опрос** (`survey.qid`). Кнопки шага – варианты ответа: callback `f:<slug>:sv:<id шага>:<N>`
  (слаг запуска обязателен – общий MAX-бот раскладывает нажатия по запускам по `f:<slug>:`),
  у multi – отметки ✅ и кнопка «готово» (`…:d`), `free` – ответ обычным сообщением (ждём 48 ч).
  На вопросе цепочка стоит (on_done / also_fire вопроса не идут), ответ → сразу шаг по стрелке
  «следующий вопрос». `final` – опрос пройден (`submitted_at`, отмена дожимов
  `z_survey_followup` / `s_survey_followup`, кнопки вопроса гасятся). `edit` – следующий текстовый
  шаг заменяет сообщение вопроса (в чате остаётся одно сообщение). Позиция, ждущая ответа, –
  «active», а не «done». *Отличия*: повторное нажатие на отвеченный вопрос игнорируется
  («Ответ уже принят», защита от двойного перехода), перезапуск воронки открывает вопрос заново;
  вопрос не ушёл (ошибка Telegram) – идём по «следующему вопросу», а не ждём ответ навсегда.
- **Звонок** (`call`: `audio_id` из кабинета > `audio_url` > синтез `text`) и **SMS** (`sms.text`
  с плейсхолдерами `{Имя}`, `{webinar.time}`, `{stream_url}` …). Номер – `participants.phone`
  (11 цифр, 7…). Итог – в `actions` (`call` / `sms`, ошибки `*_error`, пропуски `*_skipped`: нет
  провайдера, нет телефона, ключ открытым текстом), номер в логе замаскирован. Ошибка провайдера →
  цепочка дальше (on_done, also_fire). Попытка пишется в `sent_messages` до вызова провайдера:
  повтор задачи после падения процесса второй раз не звонит. Короткой прокси-ссылки
  (`/v/<код>` с автовходом в Bizon) нет – ссылка уходит как есть, в `actions.data` пометка.
- **Закреп эфира**: шаг `air_pin` (отдельное сообщение, у человека уже есть – перерисовывается) или
  обычный шаг с `pin.air_pin` (шапка с отсчётом дорисовывается над его текстом, кнопка – кнопка
  закрепа, закрепляется он сам). Состояния: ждём («4 дня до эфира» + дата сущностью `tg-time`,
  кнопка в канал) → за `soon_minutes` «скоро начинаем» (кнопка в зал) → «эфир идёт» → следующий
  эфир → все прошли (`after_text` или закреп снимается). У каждого закрепа своё `next_at` – момент
  смены состояния или гранулы отсчёта (сутки → часы → минуты); их обходит фоновая задача процесса
  раз в 15 с (`steps.periodic`) по часам движка. Дни – `air_pin.days` запуска, а без них – эфир
  самого человека из его позиции (вечнозелёный автовеб) или `webinar.datetime_msk`. *Отличия*:
  ссылка на зал без персонального прокси, значки – обычные эмодзи.
- **Статья** (`rich`, `sendRichMessage`, Bot API 07.2026; в aiogram 3.13 метода нет – описан в
  `steps/rich.py`). JSON с блоками – `media.rich` (`./rich/…` или `./static/…`: `data/media`
  Студии, затем папка запуска bot-engine). Картинки блоков заливаются служебным сообщением в
  `service_chat_id` запуска и кэшируются как file_id; служебного чата нет – блок с картинкой
  выкидывается. *Отличие*: статья не ушла – уходит текст шага (движок не слал ничего).
- **Переход в другую воронку** (`chain_to_funnel`). Важнее on_done; задержка со стрелки,
  «печатает…» сразу, если задержка > 0. Целевая воронка у человека стартует с начала (своя
  позиция, ветка и эфир по её branch_router, вход когорты), её прежние таймеры отменяются. Имя
  цели: `default` – воронка /start, прочие псевдонимы (`alt`, …) – `funnel_aliases` запуска, иначе
  id воронки. Телефон, почта и кнопки-клеймы после перехода относятся к той воронке, где их ждут.
  *Отличия*: цели нет / переход в себя / цикл – идём по on_done (движок останавливался молча);
  защита от цикла: тот же переход чаще раза в минуту или больше 10 переходов за час не выполняются
  (`chain_loop`); повтор задачи после падения второй раз воронку не перезапускает.

**В MAX** (человек пришёл через MAX-бота) виды шагов работают так же, всё, что шло через aiogram
напрямую, проверяет платформу – через Telegram человеку MAX не уходит ничего:
- **опрос** – варианты ответа кладутся в `content.max.buttons` как callback
  `f:<slug>:sv:<id шага>:<N>`: общий бот (`max_hub`) раскладывает нажатие по запуску, `sv` доходит
  до `survey.on_callback(platform="max")`. Отметки multi, «гасим кнопки» финала и `survey.edit`
  (следующий шаг на месте вопроса) – правкой сообщения `PUT /messages` (`MaxApi.edit_message`);
  правка не вышла – следующий шаг уходит новым сообщением. Свободный ответ – обычным сообщением.
  Проверено полным проходом webinar в MAX (3 вопроса и подарок – одно сообщение);
- **закреп эфира** (`air_pin` и `pin.air_pin`), `pin` – как в bot-engine (`max_runner`): закрепа в
  диалоге с ботом у MAX нет (`PUT /chats/{id}/pin` – для групповых чатов), шаг `air_pin`
  пропускается, обычный шаг уходит без шапки; в `actions` – `air_pin_skipped` / `pin_skipped`;
- **статья** (`rich`) – статей в MAX нет: уходит текст шага с его кнопками, `rich_fallback`;
- **звонок / SMS** – на телефон MAX-участника (`participants` с `platform=max`), `{stream_url}` в
  SMS – MAX-зал (`webinar.stream_url_max`, §25);
- **переход в воронку** – как в Telegram, но без «печатает…» (в MAX это действие чата, а id
  диалога движок не хранит).

### Настройки провайдеров и прочего (ключи `tenants.settings`)

Ключи провайдеров в базу **не пишутся** – только ссылка `env:ИМЯ`, как токены ботов (значение –
из окружения или `STUDIO_ENV_FILE`). Ключ, записанный открытым текстом, движок не использует
(`*_skipped` «ключ открытым текстом»).

```bash
uv run python -m runtime tenant set <slug> telephony.provider=zvonobot \
    telephony.api_key=env:ZVONOBOT_API_KEY telephony.outgoing_phone_id=123
uv run python -m runtime tenant set <slug> sms.provider=p1sms sms.api_key=env:P1SMS_API_KEY \
    sms.sender=DEMO sms.channel=char
uv run python -m runtime tenant set <slug> telephony.provider=stub sms.provider=stub  # только лог
```

| Ключ | Что |
|---|---|
| `telephony` | `provider`: `zvonobot` / `stub` / пусто (не звоним); `api_key` = `env:ИМЯ`; `outgoing_phone_id` |
| `sms` | `provider`: `p1sms` / `stub` / пусто; `api_key` = `env:ИМЯ`; `sender`, `channel` (`char` / `vk`) |
| `air_pin` | `days: [{when: "2026-09-24T11:00", title, url, subtitle, desc, live_minutes}]`, `live_minutes` (240), `soon_minutes` (30), `button_text`, `button_wait_text`, `button_wait_url` (пусто – канал), `quote`, `pin_delay_sec`, `after_text`, `emoji_*`, `text_wait` / `text_soon` / `text_live` (подстановки `{title}`, `{счётчик}`, `{осталось}`, `{через}`, `{дата}`, `{время}`, `{ссылка}`) |
| `funnel_aliases` | имя цели перехода → id воронки: `{"alt": "funnel_alt"}` |
| `service_chat_id` | чат, куда бот заливает картинки статей (бот должен туда писать) |

Боевые клиенты – `steps/providers.py` (как `services/telephony.py` и `services/sms.py` bot-engine);
свой провайдер (и фальшивый в тестах) – `providers.register("call"|"sms", имя, фабрика)`.
Списки подавления (`suppression`) bot-engine не перенесены.

## Что НЕ поддерживается (пока) и как себя ведёт

| Что | Поведение |
|---|---|
| гейты оплаты/курса/эфира/кликов без настроенного источника | «только для …» (`paid`, `course_paid`, «был», «кликнул») – **fail-safe**: шаг пропускается (`gate_failsafe`); дожимы (`not_paid`, «не был», «не кликнул») – **fail-open**: уходят (`gate_unchecked`). Публикация предупреждает |
| `has_lm`, `no_manager_dm` | источников в движке нет: `has_lm` – fail-safe, `no_manager_dm` – fail-open |
| гейт «кликнул» (`link_click`) в yaml для bot-engine | у движка bot-engine такого гейта нет – при выгрузке yaml условие теряется (предупреждение экспорта и правило 83) |
| привязка оплаты по номеру заказа со страницы «спасибо» (`viporder_`), письмо непривязанным (`vipclaim_`) | нет – только id из ссылки и (по разрешению) телефон |
| событие `paid` у человека, который дал телефон ПОСЛЕ оплаты | гейт оплату видит (читает таблицу оплат при проверке), но событие `paid` и шаг `on_paid` не запускаются – только в момент вебхука |
| гейт канала, когда бот не админ или `chat_id` = 0 | fail-open (у bot-engine тут наоборот fail-safe – шаг молча пропускался) |
| VK | не поддерживается – вкладки VK нет, боты только Telegram и MAX |
| MAX: запуск с двумя MAX-ботами | пишет людям первый привязанный бот (по id), а не тот, через который человек пришёл |
| MAX: `manual_phone_retry_text`, картинка из `{ticket_image}`, `image_lm` | нет: на «не похоже на номер» бот молчит (сообщение сохраняется), картинки шлются по шагу |
| MAX: ролик – `file_id` Telegram | в MAX не годится: видео-шаг пропускается (с `media_optional` – уходит текст), картинка – уходит текст |
| MAX: закреп эфира, `pin`, статья, «печатает…» | закрепа в диалоге с ботом и статей в MAX нет: `air_pin` пропускается, статья уходит текстом (как bot-engine) |
| MAX: вопрос опроса с картинкой/видео | отметки multi и «гасим кнопки» не рисуются (правка заменила бы вложения целиком – картинка пропала бы); ответы принимаются, повторное нажатие игнорируется |
| прокси-ссылки, когда `links` у запуска не включены; короткие `/v/` в SMS | ссылки уходят как есть; `{vip_link}` – прямая страница ВИПа (или прокси bot-engine, если задан `infra.base_url`) |
| game-модули, дожим остановленного опроса, рассылки, админ-оверрайды | нет (оверрайды заменяются версиями) |
| новые боты без рестарта | бот, добавленный при работающем движке, начнёт поллиться после рестарта (настройки и воронки – сразу) |

## Риски

- Без источника шаг «только для оплативших / бывших на эфире» теперь **не уходит никому** (fail-safe) –
  безопасно, но молча: об этом предупреждает только отчёт публикации и `gate_failsafe` в `actions`.
- Касса и люди должны дойти до HTTP-сервиса движка, а он слушает 127.0.0.1 – нужен публичный адрес
  (nginx/туннель) в `links.base_url` и в настройке вебхука кассы (задача развёртывания).
- `/go?u=<id>` не подписан: зная код и чужой id, можно «кликнуть» за другого и погасить ему дожим
  (как и в bot-engine).
- Гейт эфира ходит в Bizon в момент шага (список отчётов – не чаще `list_ttl_seconds`, зрители
  закрытой сессии – один раз): пачка шагов «был/не был» после эфира ждёт первую выгрузку отчёта.
- Не мигрируются задачи, которые выполнялись в момент публикации в режиме migrate: их продолжение
  создастся по старой версии (окно – доли секунды).
- Анти-дубль 90 с и восстановление хвоста повторяют движок, но проверяются по `actions`, а не по
  памяти процесса – при нескольких процессах это корректнее, но дороже на очень больших запусках.
- Токен в логах маскируется до первых 6 символов (это часть id бота), в `.env`-файле он открыт.
- MAX: правка сообщения (`PUT /messages`) и форма вложения «контакт» проверены на фальшивом MAX
  по документации и коду bot-engine; на живом MAX-боте Студии пока не прогонялись (боевых MAX-ботов
  трогать нельзя, своего тестового MAX-бота нет).

## Тесты

`uv run pytest tests/runtime` идёт на **настоящем Postgres** (база `fs_runtime_test` создаётся сама,
другой адрес – `STUDIO_TEST_DSN`; нет базы – тесты пропускаются), **фальшивом Telegram** (своя
aiogram-сессия записывает вызовы и умеет падать), **фальшивом MAX API** (`max_fake.py`: настоящий
HTTP-сервер aiohttp) и **управляемых часах**. Что проверяется: полный проход демо-воронки `webinar` с
порядком и секундами сообщений, телефон известен / молчит, `skip_if_past`, часы и `day_offset`, ветки
эфира, ночной режим, ошибка отправки → цепочка идёт дальше, падение процесса посреди шага → без
дубля после аренды, клейм-кнопки, повторный /start, гейты (канал, оплата, эфир, клики) на фальшивых
кассе и Bizon, публикация (отказ без карты / карта / надгробие / new-only / migrate / горячая подмена
через NOTIFY), два запуска изолированы, 600 задач разом, настоящий aiogram Dispatcher с двумя
ботами, общий MAX-бот на несколько запусков, опрос до конца в Telegram и MAX, звонки и SMS через
фальшивых провайдеров.
